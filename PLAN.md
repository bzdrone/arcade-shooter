# Design and open work

Why the project is shaped the way it is, and what is still open. Usage is in [README.md](README.md), repeatable checks in [VALIDATION.md](VALIDATION.md), toolchain knowledge in [PXT-ARCADE.md](PXT-ARCADE.md), and Portal facts and porting notes in [PORTAL.md](PORTAL.md). Git history records how the project got here.

## Purpose

- The main branch is a Battlefield 6 Portal-specific learning and authoring project, using a TypeScript-first MakeCode Arcade top-down shooter as its starting environment.
- Arcade is a **short ramp to Battlefield 6 Portal**. Creators stay long enough to understand scripting a game mode with **event handlers, functions and per-player variables**, then move to Portal. Arcade-side polish that does not serve that path (balance tuning, more maps, more weapons, demotion) is out of scope unless asked for.
- **What creators make in Arcade can be played in Portal.** A static converter page turns an exported project PNG into Portal map edits, a rules script and its strings file: the tilemap becomes an arena on the Portal Sandbox, and the selected mode plus the creator's own `mod` rules become a Portal script. This gives creators a concrete reason to build something and a visible payoff.
- The repository is the authoring environment. The latest release offers just two creator downloads: the importable **embedded-source project PNG** and **INTRO.md**, which links to optional activities online. License and activity files stay in the repository; checksums and build records stay in local release evidence. Instructions are not embedded in the PNG. Older published releases retain their original attachments.

## Architecture

1. **Engine** (`shooter.ts`, `messages.ts`, `pathing.ts`): players with per-life soldier bodies, weapons, combat, respawns, bots, scores, match end, per-player variables, HUD messages. Plain "player"/"soldier" names; creators do not program against it directly. Modes plug in with `shooter.registerMode`; the engine does not name any mode.
2. **`mod` layer** (`mod.ts`): the only creator-facing scripting surface. It copies Portal's `mod` names, argument order and event shapes for the subset game modes need. Portal overloads become one function with a union parameter (`Team | Player`) dispatched with `instanceof`.
3. **Compatibility libraries** for Portal systems too large to mirror:
   - **Weapons** (`weapons.ts`): four categories (pistol, SMG, shotgun, knife) mapped to Arcade stats; the Portal side maps each to one real item and inventory slot. Portal's full weapon enum and real gun names are not mirrored.
   - **Messages** (in `mod`): `Message` with `{}` placeholders, notifications and large announcements, drawn as timed, non-blocking HUD queues instead of Portal's widget UI.
4. **Modes** (`deathmatch.ts`, `gungame.ts`): written against `mod` and `weapons`, so they double as worked examples that read almost like Portal scripts. "No mode" leaves the rules to the creator.

5. **Arcade to Portal converter** (`site/`): a static page with no backend and no external libraries. `site/converter/` reads the project PNG (its own PNG and LZMA decoders), builds a `.spatial.json` from the tilemap, and translates the rules by applying PORTAL.md's porting checklist as text edits on the creator's own code. A bundled Portal runtime (`portal-runtime.ts`) supplies what the Arcade engine did: bots, settings, numbered variables and the weapon categories. `tools/convert-portal.mjs` runs the same code from the command line.

The Arcade `mod` learning API and converter target Battlefield 6 Portal. The converter translates the supported maps and rules into Portal files; PORTAL.md records the concrete API differences, conversion limits, and runtime facts it relies on. `portal/gungame.ts` remains as the hand-written port the converter's output was modelled on.

## Design decisions

- **Teams:** even 2v2, blue human plus one friendly bot against two red bots, all called soldiers. Bots move at 10 px/s, the human at 70 px/s. Ranged damage only, distinct team spawn tiles, five-second respawns including the human.
- **Deathmatch:** first team to ten eliminations. Self and friendly eliminations do not score.
- **Gun game:** individual ladders (pistol → SMG → shotgun → knife); the first player to score a knife elimination wins for their team. A late shot from a player's previous weapon still damages but does not advance them, which needs an extra `eventWeapon` kill-event parameter that Portal lacks (a listed porting fix-up).
- **Weapons:** no sniper or rifle, one automatic weapon. Range caps shot lifetime; bots close to within range before firing. Shotgun is one heavy short-range shot and knife a very short-range projectile; there is no spread or separate melee system.
- **Maps and camera:** the original default yard stays unchanged at 10×7 with 16-pixel tiles. A separate 25×19 `combatCompound` sample adds room wings, doorways, courtyard cover and flanking routes. Maps are assets, selected before startup independently of mode; every mode can use every valid map. Larger maps scroll with the human soldier, clamped at map edges. Death holds the last view until respawn binds the new body. Soldiers are constrained by map walls, not the viewport; shots remain active off screen until impact/range expiry. Health bars use camera-relative positions; the HUD stays screen-fixed. A disposable 30×20 map exercises scrolling; this is not a performance guarantee for arbitrary map sizes.
- **Messages:** two kinds (short notifications and large announcements). The bottom health/respawn line stays engine-only. In the human's view, messages aimed only at bots or the red team are dropped.
- **mod layer:** Portal team numbering (team 1 blue, team 2 red); everything in `mod`, with no separate `modlib` namespace; plain MakeCode event blocks with draggable parameters named as in Portal (`eventPlayer`, `eventOtherPlayer`, `eventWeapon`). Game start and initial deployments are delivered on the first frame, so handlers placed anywhere in a program receive them.
- **Blocks:** keep existing block IDs stable; only configuration, mode selection, Mod and Weapons blocks are creator-facing.
- **First experience:** creators new to MakeCode Arcade work through a few beginner tutorials, then practice saving a tutorial game as a project PNG and importing it again, checking that their blocks and a recognizable change survive. The shooter introduction focuses on playing and changing incoming damage percent in an existing block, with no code editing or mode selection. Activity 1 introduces health, respawn delay, and friendly fire one at a time in Blocks. Game-mode scripting comes later; the first session does not require finishing a match or reading the engine source.
- **The Portal port experiment** lives in `portal/`, outside the PNG manifest and the creator path.
- **Converter delivery:** a static site so it can be hosted anywhere (GitHub Pages intended) and nothing leaves the creator's browser. No dependencies: a PNG reader and an LZMA decoder (checked against MakeCode's compressor) were cheaper than adding libraries. The page and the command line share one implementation and must produce identical files.
- **Converted map:** always `MP_Portal_Sand`, centred on the origin, one tile = 4 m, at most 50 × 50 tiles. Each wall-marked tile becomes one 10 m stone block; wall-marked tiles whose image name contains "cover" become 3 × 3 chest-high blocks (Arcade cover blocks shots, but low cover plays better in first person); blue/red spawn tiles become team 1/2 HQ spawn points and bot spawner locations; the map edge plus 6 m becomes the combat area. Ground height comes from a sampled terrain grid.
- **Converted rules:** registered handlers become functions called from exported Portal events, in Arcade's registration order; waits become `await mod.Wait`, with `async` propagated through functions that wait; message text and text arguments move to the strings file, and `"text" + value` joins become `{}` placeholders. Statements using Arcade-only APIs are commented out with a note rather than failing the conversion.
- **Converted behaviour:** bots fill each team to two soldiers, counting humans; a bot keeps a "seat" across lives so its variables, weapon and kill counts persist as in Arcade. Variables, scores and the target score (Portal would end the round at the target; in Arcade only the rules end a match), `EndGameMode` (a player wins for their team), `DealDamage` (Arcade health points) and kill/death counts go through the runtime. Declarative maximum health, incoming damage percent, respawn seconds, and friendly fire feed SDK runtime actions. Bot speed maps to a move speed for legacy settings. Everyone starts with the pistol unless mode rules equip another category; Arcade fire interval no longer selects a weapon, and Arcade projectile speed is not converted. In kill events `eventWeapon` is the killer's current category.

## Modifier convention

- Keep declarative experience modifiers separate from map selection and event-driven mode rules. Expose a small `modifiers` namespace with matching Blocks: `setMaxHealth`, `setIncomingDamagePercent`, `setRespawnSeconds`, and `setFriendlyFire`.
- Apply modifiers before `startGame()`, initially to everyone. Use literal numbers/booleans, explicit defaults, and last-setting-wins semantics. The converter must report unsupported or nonliteral settings rather than silently guessing. Dynamic per-player effects remain scripting actions, not configuration.
- Treat incoming damage as a percentage with 100 meaning normal (a working assumption). Keep firing intervals and projectile speed internal to Arcade; do not infer a different weapon from firing interval. Leave movement-speed modifiers out initially.
- Arcade and the converter apply matching validation/defaults, checked by parity tests: health 100 (rounded/clamped 1–500), incoming damage 100 percent (rounded to steps of 5, clamped 0–200), respawn 5 seconds (clamped 0–60, fractions retained), friendly fire false. Configuration locks at startup. Arcade's simplified weapons use 34 damage for pistol/SMG and 100 for shotgun/knife, retaining the three-hit baseline at 100 health. Friendly eliminations never award a kill or advance the built-in modes.
- Portal output applies these values through SDK runtime actions, not a website modifier-import file. Absolute health and respawn seconds differ from Builder's multipliers; damage percent is not separate head/body damage. Import serialization remains deferred until an accepted example establishes the schema. No JSON fields are invented.
- The opening example and first activity use experience modifiers rather than Arcade weapon timing/speed. Legacy Shooter settings/IDs remain for compatibility. Keep movement/projectile speed, regeneration, team-specific settings, and headshot/body-shot multipliers out of the initial subset. Use reasonable SDK-based approximations; investigate Portal behavior when a concrete blocker appears.

## Not yet verified

- **Converter output in Portal:** the author playtested converted gun game on the larger compound and confirmed weapon progression and a readable replacement score panel. Weapon-level persistence across respawn and the final knife-elimination win remain unconfirmed; broader checks below are deferred, not prerequisites for more investigation now. Remaining checks include whether deathmatch and gun game on the converted training yard load and play: two soldiers per team, bots respawning from their own spawners, a score header, weapon changes that work in play, spawn facing and wall and cover heights that look right, and bots matched to seats although Portal reuses player ids. The latest runtime keeps scores and the target itself because Portal previously ended a gun game round at the target score; its final knife-elimination behavior passes simulation but remains unconfirmed in live play. Not checked: whether the web builder steps on the page are right, bot names on the scoreboard, a full gun game match to a knife kill, other creator-edited maps beyond the sample yard/compound, and creator rules beyond the built-in modes.
- **Converter hosting:** a portable build (`tools/build-site.mjs`) and manual-only GitHub Pages workflow are prepared; see SITE.md. The page runs locally (`tests/portal-site.cjs`) but is not published. Enabling Pages and running deployment require publication approval.
- **Portal port experiment:** `portal/gungame.ts` passes the SDK 2.1.2.0 type check but has never run in Portal. Unknown: player `ObjectVariable` slots without editor declarations, weapon swap feel, how numbers display in messages.
- **Creators:** neither lesson has been tried with a creator. The published baseline was playtested by the author and played well; that is not creator evidence.
- **Balance:** no natural full gun-game match has been played. The human's speed advantage matters more with individual ladders (kiting bots, especially at the knife stage), and blue's team win often depends on the human. Tune only from feedback.
- Browser checks use synthetic input and controlled placements, not physical keyboards or natural matches.
